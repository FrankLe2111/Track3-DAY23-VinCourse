2. Mục tiêu và cách chấm

Agent nhận một support ticket, phân loại ý định bằng LLM, chọn nhánh xử lý, có thể gọi mock tool, đánh giá kết quả, retry khi lỗi, xin phê duyệt khi có side effect, rồi luôn kết thúc ở bước audit cuối.

3. Kiến trúc graph cần đạt

Graph có một đường vào chung, một điểm phân loại, các nhánh chuyên biệt và một điểm kết thúc chung. Điểm đáng học nhất là LangGraph cho phép biểu diễn retry loop bằng conditional edge thay vì tự viết vòng lặp ngoài.

START
  │
  ▼
intake ──> classify ── route_after_classify ──┬── simple ───────> answer ──┐
                                                    ├── tool ─────────> tool ────┤
                                                    ├── missing_info ─> clarify ──┤
                                                    ├── risky ───────> risky_action → approval ─┐
                                                    └── error ───────> retry ─────────────────────────┤
                                                                                                         ▼
                       tool ──> evaluate ── route_after_evaluate ──┬── success ─────> answer
                                                                             └── needs_retry ─> retry

retry ── route_after_retry ──┬── attempt < max_attempts ──> tool (lặp)
                                 └── attempt ≥ max_attempts ─> dead_letter

approval ── route_after_approval ──┬── approved ──> tool ─> evaluate ─> ...
                                       └── rejected ──> clarify

answer / clarify / dead_letter ──> finalize ──> END

Fixed edge và conditional edge

LoạiEdge cần cóÝ nghĩa
FixedSTART → intake → classifyChuẩn hóa query trước khi phân loại.
Conditionalclassify → route_after_classifyChọn một trong năm nhánh nghiệp vụ.
Fixedtool → evaluateTool luôn phải được kiểm tra kết quả.
Conditionalevaluate → route_after_evaluateKết quả tốt thì trả lời; lỗi thì retry.
Conditionalretry → route_after_retryGiới hạn số lần thử, quá giới hạn thì dead letter.
Conditionalapproval → route_after_approvalChỉ action đã được duyệt mới đi tiếp đến tool.
Fixedanswer/clarify/dead_letter → finalize → ENDĐảm bảo mọi route đều có audit event cuối và terminate.

4. State schema và reducer

AgentState là TypedDict(total=False). Các node không mutate state đầu vào; mỗi node chỉ trả về partial state update. LangGraph merge update vào state hiện tại.

FieldReducer hiện có / cần dùngVai trò
thread_idoverwriteKhóa persistence cho từng run; CLI đặt là thread-<scenario.id>.
scenario_id, queryoverwriteĐịnh danh và nội dung ticket.
route, risk_leveloverwriteKết quả phân loại hiện tại; route cuối vẫn phải giữ expected route, kể cả khi đi dead_letter.
attempt, max_attemptsoverwriteBộ đếm retry và trần retry. retry_or_fallback_node tăng attempt.
final_answeroverwriteCâu trả lời cuối từ LLM, clarification hoặc dead-letter fallback.
messagesAnnotated[list[str], add]Lịch sử message/audit ngắn; node append thêm, không thay thế.
tool_resultsAnnotated[list[str], add]Lưu từng kết quả tool, gồm cả kết quả lỗi qua các lần thử.
errorsAnnotated[list[str], add]Danh sách lỗi để metrics và dead-letter diagnosis.
eventsAnnotated[list[dict], add]Audit trail chính; metrics đếm node/retry/approval từ đây.
evaluation_resultoverwriteField bắt buộc bổ sung; giá trị tối thiểu: success hoặc needs_retry.
pending_questionoverwriteCâu hỏi cần hỏi thêm trong nhánh missing_info hoặc approval reject.
proposed_actionoverwriteMô tả side effect trước khi xin approval.
approvaloverwriteQuyết định HITL; nên giữ cấu trúc serializable tương ứng ApprovalDecision.
Nguyên tắc reducer: event, messages, tool results và errors là dữ liệu lịch sử nên append; route, attempt, evaluation và approval là trạng thái hiện tại nên overwrite. Không đưa object LLM client hoặc callback không serializable vào state.

6. Routing, retry và HITL

4 hàm routing

HàmĐiều kiệnNode trả về
route_after_classifyroute = simple/tool/missing_info/risky/erroranswer/tool/clarify/risky_action/retry; unknown mặc định answer.
route_after_evaluateevaluation_result == "needs_retry"retry; mọi giá trị khác đi answer.
route_after_retryattempt < max_attemptstool; ngược lại dead_letter.
route_after_approvalapproval.approved is Truetool; false hoặc thiếu approval đi clarify.

Trace retry của S05

classify(route=error) → retry(attempt 0→1) → tool(ERROR) → evaluate(needs_retry)
→ retry(attempt 1→2) → tool(ERROR) → evaluate(needs_retry)
→ retry(attempt 2→3) → tool(success) → evaluate(success) → answer → finalize → END

Với max_attempts=3, sau lần retry thứ ba, attempt bằng 3 nhưng vẫn đi lại tool vì điều kiện được kiểm tra sau khi node retry tăng bộ đếm; tool lần này thành công do mô phỏng lỗi chỉ áp dụng khi attempt < 2. Đây là cách trace được suy ra trực tiếp từ yêu cầu node và routing.

Trace dead letter của S07

classify(route=error) → retry(attempt 0→1) → route_after_retry → dead_letter
→ finalize → END

S07 đặt max_attempts=1, nên không cần gọi tool. Route trong state vẫn là error để metrics so sánh với expected route; dead_letter là node xử lý kết thúc, không nhất thiết là giá trị route classification.

Trace risky/HITL của S04 hoặc S06

classify(route=risky) → risky_action → approval(approved=True)
→ tool → evaluate(success) → answer → finalize → END

Nếu approval bị reject: approval → clarify → finalize → END. Không được cho risky action chạy thẳng đến tool trước khi có approval event.

8. LLM, persistence, metrics và report

LLM

llm.py chọn provider theo thứ tự GEMINI_API_KEY, OPENAI_API_KEY, ANTHROPIC_API_KEY. Model có thể override bằng LLM_MODEL.

Provider package là optional extra trong pyproject.toml, nên phải cài đúng provider. classify_node cần schema Pydantic/TypedDict; answer_node cần truyền query, tool results và approval context vào prompt.

Điểm cần tự xử lý: .env.example hướng dẫn tạo .env, nhưng llm.py hiện chỉ đọc os.getenv và không gọi load_dotenv(). Vì vậy cần export biến môi trường trước khi chạy, hoặc bổ sung cơ chế load .env nếu chọn cách đó.

Persistence

persistence.py đã có MemorySaver; đây là default trong configs/lab.yaml. SQLite là extension 10 điểm persistence/recovery.

CLI truyền {"configurable": {"thread_id": state["thread_id"]}} vào graph.invoke. Muốn chứng minh recovery cần dùng SQLite/checkpoint history hoặc mô phỏng crash-resume, rồi đặt resume_success=True khi có bằng chứng thật.

report.py phải render Markdown theo template trong reports/lab_report_template.md. File HTML này là tài liệu hiểu bài; không thay thế file submission reports/lab_report.md mà CLI sẽ tạo sau khi metrics hợp lệ.

10. Lộ trình triển khai ít rủi ro

  1. Chuẩn bị môi trường: tạo venv, cài pip install -e '.[dev]' và một provider extra; export một API key. Chạy test state/metrics trước.
  2. Mở rộng state: thêm bốn field được docstring yêu cầu; giữ list history dùng reducer add, field scalar dùng overwrite.
  3. Viết routing trước: đây là phần nhỏ, test có sẵn bao phủ mapping và bound retry.
  4. Viết node offline trước: tool, evaluate, clarification, risky action, mock approval, retry, dead letter, finalize. Mỗi node append event có node name đúng.
  5. Viết hai node LLM: structured classifier và grounded answer. Không match scenario ID, không hard-code câu trả lời.
  6. Wire graph: đăng ký đủ 11 node, fixed edges, conditional edges; compile với checkpointer.
  7. Chạy graph smoke: test 5 loại route, kiểm tra mọi event có finalize; sau đó chạy 7 sample scenarios.
  8. Kiểm tra metrics: chạy make grade-local; soi riêng retry, approval và S07 dead letter.
  9. Hoàn thiện report: tạo reports/lab_report.md với architecture, bảng metrics, hai failure mode, persistence evidence và improvement plan.
  10. Chọn extension: nếu cần 90+, ưu tiên SQLite + crash-resume hoặc state history vì chúng trực tiếp ăn điểm persistence; interrupt thật/diagram là phần mở rộng sau.
