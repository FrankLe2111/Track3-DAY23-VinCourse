1. Tổng quan dự án

Dự án xây dựng một workflow agent chuẩn production bằng LangGraph để xử lý support ticket (phiếu hỗ trợ khách hàng). Thay vì một chuỗi xử lý tuyến tính, hệ thống được mô hình hóa thành đồ thị trạng thái (state graph) với:

  • Phân loại ý định bằng LLM (structured output) thay vì so khớp từ khóa;
  • Định tuyến điều kiện theo 5 route: simple, tool, missing_info, risky, error;
  • Vòng retry có giới hạn cho lỗi tạm thời của tool, kèm dead_letter khi cạn retry;
  • Human-in-the-loop (HITL): hành động rủi ro (refund, xóa tài khoản, gửi email) phải qua bước phê duyệt;
  • Persistence bằng SQLite checkpointer — mỗi lượt chạy một thread_id, hỗ trợ xem lịch sử trạng thái;
  • Metrics tự động: tỉ lệ thành công, số node đi qua, số retry, số interrupt, độ trễ từng scenario.
Kết quả tổng thể: 7/7 scenarios định tuyến đúng (success rate 100%), 28/28 tests pass, lint (ruff) và typecheck (mypy) sạch, metrics hợp lệ theo schema MetricsReport, có 3 tính năng mở rộng vượt yêu cầu cơ bản.

2. Kiến trúc graph

Graph gồm 11 node, biên dịch bằng StateGraph(AgentState) và compile(checkpointer=...). Mọi đường đi đều kết thúc tại finalize → END.

2.1. Sơ đồ luồng thực tế (export từ graph đã compile)

graph TD; __start__([START]):::first intake(intake) classify(classify) tool(tool) evaluate(evaluate) answer(answer) clarify(clarify) risky_action(risky_action) approval(approval) retry(retry) dead_letter(dead_letter) finalize(finalize) __end__([END]):::last __start__ --> intake; intake --> classify; classify -.-> answer; classify -.-> clarify; classify -.-> retry; classify -.-> risky_action; classify -.-> tool; tool --> evaluate; evaluate -.-> answer; evaluate -.-> retry; retry -.-> dead_letter; retry -.-> tool; risky_action --> approval; approval -.-> clarify; approval -.-> tool; answer --> finalize; clarify --> finalize; dead_letter --> finalize; finalize --> __end__;

Cạnh liền = cạnh cố định (fixed edge); cạnh đứt = cạnh điều kiện qua hàm routing. Sơ đồ này được sinh tự động bằng graph.get_graph().draw_mermaid() (xem mục 11 — Extensions).

2.2. Các đường đi theo route

RouteĐường đi trong graphÝ nghĩa
simpleintake → classify → answer → finalize → ENDCâu hỏi thông tin, trả lời trực tiếp bằng LLM
toolintake → classify → tool → evaluate → answer → finalize → ENDTra cứu dữ liệu (order, tracking) qua mock tool
missing_infointake → classify → clarify → finalize → ENDYêu cầu mơ hồ → hỏi lại bằng LLM thay vì đoán
riskyintake → classify → risky_action → approval → tool → evaluate → answer → finalize → ENDHành động có side-effect, bắt buộc qua phê duyệt
errorintake → classify → retry → tool → evaluate → (loop) → answer/dead_letter → finalize → ENDLỗi hệ thống → retry có giới hạn → dead letter nếu cạn

4. Thiết kế State Schema

AgentState là TypedDict gọn nhẹ, serialize được, gồm 16 trường. Nguyên tắc: trường lịch sử dùng reducer append-only (Annotated[list, add]), trường giá trị hiện tại ghi đè.

TrườngKiểu / reducerVai tròNguồn
thread_id, scenario_id, querystr (overwrite)Định danh lượt chạy và câu hỏi đầu vàoStarter
routestr (overwrite)Route do classify_node quyết địnhStarter
risk_levelstr (overwrite)high/low — high khi route = riskyStarter
attempt, max_attemptsint (overwrite)Bộ đếm retry và ngưỡng tối đa (mặc định 3)Starter
final_answerstr | NoneCâu trả lời cuối cùng cho người dùngStarter
evaluation_resultstr | None"success"/"needs_retry" — cổng của vòng retrySinh viên thêm
pending_questionstr | NoneCâu hỏi làm rõ khi thiếu thông tinSinh viên thêm
proposed_actionstr | NoneMô tả hành động rủi ro chờ phê duyệtSinh viên thêm
approvaldict | NoneQuyết định HITL: approved / reviewer / commentSinh viên thêm
messageslist[str] · addNhật ký thông điệp nội bộStarter
tool_resultslist[str] · addKết quả từng lần gọi toolStarter
errorslist[str] · addNhật ký lỗi / lần retryStarter

Vì sao chọn append-only cho 4 trường cuối? Vòng retry quay lại node tool nhiều lần; nếu ghi đè sẽ mất dấu vết các lần thất bại trước đó và metrics (retry_count, errors) sẽ sai. Reducer add của LangGraph nối list cũ + list mới, giữ nguyên toàn bộ audit trail.

7. Tích hợp LLM

Hệ thống dùng LLM thật (OpenAI gpt-5.6-sol, key đọc từ .env qua python-dotenv) tại 3 node — đúng yêu cầu chấm điểm "không keyword-only, không hardcode":

7.1. classify_node — structured output

class Classification(BaseModel):
    route: Literal["simple", "tool", "missing_info", "risky", "error"]
    risk_level: Literal["low", "high"] = "low"

classifier = get_llm(model=...).with_structured_output(Classification)
result = classifier.invoke(prompt)   # LLM buộc trả về enum hợp lệ
  • Prompt liệt kê định nghĩa từng route và thứ tự ưu tiên khi tín hiệu chồng nhau: risky > tool > missing_info > error > simple — quan trọng để đúng với các scenario ẩn của giám khảo (ví dụ "Refund ... and lookup order" phải là risky).
  • Structured output đảm bảo không phải parse text thô — tránh lỗi fragile trên input lạ.

7.2. answer_node — grounded generation

Prompt đưa toàn bộ context (query, route, tool_results, approval) dưới dạng JSON và ra ràng buộc: "chỉ trả lời dựa trên context, không bịa thông tin đơn hàng/refund; nếu tool báo lỗi thì nói rõ và đề xuất bước an toàn tiếp theo".

7.3. ask_clarification_node

Sinh đúng một câu hỏi làm rõ cụ thể, cấm đoán ý người dùng — thể hiện nguyên tắc "không hallucinate khi thiếu thông tin".

7.4. evaluate_node

Hiện dùng heuristic (kiểm tra chuỗi ERROR) — mức base score theo rubric. LLM-as-judge là hướng nâng cấp (mục 13).

8. Persistence & khôi phục

  • build_checkpointer("sqlite") dùng SqliteSaver(conn=sqlite3.connect(...)) với PRAGMA journal_mode=WAL (đúng API của langgraph-checkpoint-sqlite 3.x, không dùng from_conn_string đã deprecated).
  • Mỗi scenario chạy với thread_id riêng (thread-<scenario_id>) — checkpoint của từng run tách biệt trong checkpoints.db.
  • Sau mỗi lượt invoke, CLI gọi graph.get_state_history(config): chỉ khi lịch sử checkpoint thật sự tồn tại thì resume_success=true — metrics gắn với bằng chứng, không phải lời khẳng định.
  • CLI xóa file checkpoint cũ trước mỗi đợt run-scenarios để số liệu (events/errors append-only) không bị cộng dồn giữa các lần chạy — đảm bảo metrics lặp lại được.

11. Các tính năng mở rộng (bonus — yêu cầu cho nhóm điểm 90–100)

11.1. HITL thật bằng interrupt()/resume

Khi đặt LANGGRAPH_INTERRUPT=true, approval_node gọi langgraph.types.interrupt() thay vì tự duyệt. Graph tạm dừng trước khi thực thi hành động rủi ro; người duyệt tiếp tục bằng graph.invoke(Command(resume={"approved": ...})). Được kiểm chứng end-to-end bởi 3 test trong tests/test_hitl_interrupt.py:

  • Pause: state có __interrupt__, tool chưa chạy, chưa có final_answer;
  • Resume-approve: tool chạy, câu trả lời sinh ra, đi tới finalize;
  • Resume-reject: tool không bao giờ chạy, chuyển sang hỏi làm rõ.

11.2. SQLite persistence + state-history replay

Checkpointer SQLite (WAL) lưu toàn bộ checkpoint theo thread_id; resume_success trong metrics chỉ bật khi get_state_history() trả về checkpoint thật sau khi chạy — bằng chứng khôi phục/xem lại trạng thái.

11.3. Export sơ đồ Mermaid

Lệnh python -m langgraph_agent_lab.cli diagram xuất sơ đồ graph đã compile ra outputs/graph_diagram.md; run-scenarios tự nhúng sơ đồ vào reports/lab_report.md. Sơ đồ ở mục 2.1 của báo cáo này chính là output đó.

13. Phân tích lỗi & hướng cải tiến

13.1. Các failure mode đã xử lý

  1. Lỗi tool tạm thời: kết quả chứa ERROR → evaluate đánh needs_retry → retry tăng attempt → chỉ quay lại tool khi attempt < max_attempts, ngược lại vào dead_letter (chứng minh bởi S05 tự phục hồi, S07 dead-letter).
  2. Hành động rủi ro chưa duyệt: refund/xóa/gửi email đi qua approval; reject → clarify, không bao giờ chạm tool (test resume-reject chứng minh).
  3. Yêu cầu mơ hồ: hỏi làm rõ bằng LLM thay vì bịa câu trả lời (S03).
  4. Metrics bị cộng dồn khi chạy lại: do checkpointer SQLite giữ append-only state theo thread_id cũ — đã sửa bằng cách reset DB mỗi đợt run-scenarios.

13.2. Hướng cải tiến

  • Dùng LLM-as-judge cho evaluate_node thay heuristic chuỗi ERROR;
  • Thay mock tool bằng adapter thật có xác thực + idempotency key;
  • UI Streamlit cho duyệt/từ chối trên interrupt thật;
  • Parallel fan-out bằng Send() khi cần gọi nhiều tool đồng thời;
  • Thêm metrics token/chi phí LLM và test hồi quy trên bộ scenario ẩn.
